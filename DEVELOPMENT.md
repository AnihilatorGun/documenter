# Documenter изнутри

Как приложение устроено, почему устроено именно так, и что осталось.
Про установку и пользование — в [README.md](README.md).

## Как устроено

Всё, что нужно хранить, лежит в Google Drive, в одной папке `Documenter`:

* **файлы** — сканы и фотографии документов;
* **индекс** — файл `documenter-index.db`, где записано, что это за документы:
  чьи они, какие теги, языки, сроки, заметки.

Приложение — только инструмент работы с этой папкой, своего у него ничего нет.
При запуске оно скачивает индекс в `data/documenter.db`, работает с этой копией
и после каждого изменения заливает её обратно.

Почему так, а не «просто разложить по папкам в Drive»: как только пробуешь выразить
фильтр «все документы Ани с тегом виза» через вложенные папки, всё превращается
в кашу. Поэтому индекс — база SQLite. А SQLite не умеет работать прямо в Drive:
ей нужен локальный файл, в который она пишет по кусочкам и который блокирует.
Отсюда и схема «скачал — поработал — залил».

Единственное, что остаётся только на компьютере и никуда не уезжает, — файл
`data/local_state.json` с разрешением на доступ к Drive. Это сделано нарочно:
во-первых, без него нечем скачать сам индекс, во-вторых, благодаря этому копия
индекса в Drive не содержит ничего секретного.

### Синхронизация между копиями

Приложение спрашивает у Drive, не изменился ли индекс: перед каждым сохранением
обязательно, а при обычной навигации не чаще раза в 15 секунд — иначе каждый клик
ждал бы ответа Google лишнюю четверть секунды. Проверка версии дешёвая, скачивание
происходит только когда версия действительно разошлась.

Скачанный индекс вливается в уже открытое соединение SQLite, а не подменяет файл
на диске: подмена файла под работающим приложением сломала бы открытые запросы.

Что всё-таки может пойти не так: настоящих блокировок Drive не даёт, так что если
двое одновременно держат открытой форму одного и того же документа, победит тот,
кто нажмёт «Сохранить» вторым. Приложение это заметит и покажет предупреждение,
а прежнюю версию индекса можно достать из истории версий файла в Drive.

Если Drive недоступен в момент запуска, приложение работает с локальной копией,
но **перестаёт заливать изменения**, чтобы не затереть чужую работу базой, которую
оно не смогло прочитать.

## Разработка

```
make run     # сервер с перезапуском при правке кода
make test    # тесты
```

Пощупать приложение можно без всякого Google: запустить без файла `.env`. Файлы
лягут в папку `data/files`, а на странице входа появится кнопка «Просто посмотреть
приложение». Она исчезает сама, как только в `.env` появляется `GOOGLE_CLIENT_ID`.

Останавливать сервер нужно `Ctrl+C`. `Ctrl+Z` только приостанавливает его, и порт
8000 остаётся занятым — тогда при следующем запуске будет «address already in use»,
а вылечит её `kill -9 $(lsof -t -i:8000)`.

## Из чего состоит код

Читать в этом порядке — каждый следующий файл опирается на предыдущие.

| Файл | Что внутри |
|---|---|
| `documenter/models.py` | описание данных: Document, Person, Tag, StoredFile и справочники языков и тегов по умолчанию |
| `documenter/schema.sql` | таблицы SQLite один в один под эти данные |
| `documenter/db.py` | подключение к базе, создание таблиц, пара функций для настроек |
| `documenter/local_state.py` | то немногое, что хранится только на этом компьютере |
| `documenter/repo.py` | все SQL-запросы: создать, прочитать, обновить, удалить, отфильтровать |
| `documenter/storage.py` | что приложение ждёт от хранилища файлов, и простая реализация «папка на диске» |
| `documenter/google_oauth.py` | вход через Google и получение доступа к Drive |
| `documenter/drive.py` | то же хранилище файлов, но поверх Google Drive |
| `documenter/sync.py` | скачивание индекса из Drive и заливка обратно |
| `documenter/invite.py` | сборка и разбор приглашения на второй компьютер |
| `documenter/config.py` | настройки из `.env` |
| `documenter/auth.py` | проверка, что пользователь вошёл |
| `documenter/app.py` | веб-страницы и формы, которые связывают всё вышеперечисленное |
| `documenter/templates/` | HTML-страницы |

`repo.py`, `storage.py`, `drive.py` и `sync.py` намеренно не знают ничего про веб.
Из-за этого их можно вызвать откуда угодно — например из будущего MCP-сервера,
см. «Что дальше».

## Принятые решения

* **Одно приложение = одна семья.** Никаких аккаунтов, организаций и разделения:
  кто вошёл, тот видит все документы всех.
* **Кто может войти** — список почт в `.env`. Не в базе, потому что список
  меняется раз в год, а править файл проще, чем делать экран администратора.
* **Файлы лежат в Drive владельца**, а не у каждого своего. Одна папка, одна квота,
  ничего не нужно расшаривать. Остальные члены семьи скачивают файлы через
  приложение, их собственный Drive не участвует.
* **Приложение просит у Google минимальный доступ** — только к файлам, которые
  создало само. Остальные документы в Drive для него невидимы.
* **Хранилище файлов спрятано за одним интерфейсом** (`storage.py`), поэтому
  «папка на диске» и «Google Drive» взаимозаменяемы. Первое — для разработки
  и первого знакомства, второе — для жизни.
* **Истина живёт в Drive, а не на компьютере.** Локальная база — рабочая копия,
  которую не жалко потерять. Поэтому отдельного «бэкапа» в системе нет: копия
  обновляется сама после каждого изменения.
* **Вторая копия ходит в Drive под учётной записью владельца.** Причина не в лени:
  минимальные права выдаются на пару «приложение + конкретный человек», поэтому
  аккаунт второго человека не увидит файлы владельца, даже если расшарить папку —
  для Google это чужие файлы, созданные не в его сессии. Обойти это можно либо
  встроив гугловый диалог выбора файлов (JavaScript-виджет, и выбирать файлы
  пришлось бы руками), либо попросив полный доступ ко всему Диску — а за это Google
  требует платный аудит безопасности и показывает предупреждение во весь экран.
  Перенести разрешение оказалось меньшим злом: оно даёт доступ ровно к той папке,
  которой вы и так делитесь.
* **Ключ к приглашению генерируется случайно, а не придумывается человеком.**
  Так не нужно решать, достаточно ли надёжный пароль придумал пользователь,
  и не нужен механизм превращения пароля в ключ шифрования.
* **Никакого JavaScript-фреймворка.** Обычные HTML-формы и серверный рендеринг:
  меньше кода, нечего собирать, работает с телефона.

## Чего нет

Сознательно не сделано, чтобы не разрастаться: распознавание текста со сканов,
напоминания на почту или в телеграм, история версий документа, публичные ссылки
наружу, мобильное приложение.

## Что дальше

**MCP-сервер.** Идея: дать агенту (например Claude) доступ к документам, чтобы
он сам находил нужные бумаги и заполнял по ним анкеты. Понадобится отдельный
небольшой файл рядом с `app.py`, который выставит наружу три действия: найти
документы по фильтрам, показать карточку, отдать содержимое файла. Всё это уже
есть в `repo.py` и `storage.py` и не требует их переделки — именно поэтому они
не знают про веб.

**Одна установка на семью.** Сейчас у каждого своя копия, и они синхронизируются
через Drive. Альтернатива — держать приложение в одном месте, а остальным открывать
его в браузере: тогда конфликтов не бывает в принципе. Нужен постоянный адрес
с настоящим `https` (Google пускает по `http` только на `localhost`) и всегда
включённая машина — домашний сервер или приватная сеть вроде Tailscale.
